# 执行路线图：从当前状态到可演示 MVP

## 1. 先确定方向

当前项目已经有后端、前端、登录认证、笔记、Markdown 文件、切片和 Milvus 索引，但还缺少一条从用户操作到业务结果的完整链路。接下来不再同时铺开所有计划功能，先完成一个可以演示、可以测试、可以说明 RBAC 价值的最小产品：

```text
用户注册/登录
    ↓
创建或进入知识库
    ↓
上传 Markdown 资料
    ↓
资料切片、向量化、建立索引
    ↓
在有权限的知识库中提问
    ↓
返回答案和引用资料
```

RBAC 放在“知识库成员和资料访问”上验证，而不是只做一个没有业务内容的管理员按钮。

## 2. 当前状态判断

### 已有基础

- Spring Boot + Vue 工程可以运行；
- MySQL、Redis、Milvus 等本地依赖已经配置；
- 统一响应、异常处理和 JWT 登录框架已经存在；
- `ROLE_USER`、`ROLE_ADMIN`、角色表、权限表和权限注解已经存在或正在完善；
- 笔记 CRUD 和 Markdown 双栏编辑器已经存在；
- Markdown 文件上传、删除、预览和重索引已经存在；
- 文档切片、Embedding、Milvus 写入和索引状态已经存在；
- 已有后端和前端测试基础。

### 当前主要问题

- 认证相关改动很多仍在工作区，尚未形成稳定基线；
- README、架构文档和实际代码的完成范围不完全一致；
- 没有知识库实体，资料没有业务归属范围；
- 没有问答接口，因此索引流水线还没有用户可见的业务结果；
- RBAC 只有全局管理员雏形，缺少项目/知识库级权限；
- 标签、搜索、分享、主题等功能尚未形成主流程。

## 3. 暂时冻结的内容

在 MVP 完成前，暂时不做以下内容：

- 仿照禅道实现完整项目管理系统；
- 复杂的角色编辑器和动态权限配置页面；
- 标签、主题、分享、邮件真实发送等非主流程功能；
- 多模型切换、复杂混合检索和高并发优化；
- 将所有现有代码重构成新的架构。

保留已有代码，但不再扩展这些方向，避免项目继续发散。

## 4. 执行原则

每个阶段都必须同时具备：

1. 后端接口；
2. 前端最小页面；
3. 自动化测试；
4. 可手工演示的验收步骤；
5. 一次独立提交。

每完成一个阶段再进入下一个阶段。不要先写大量数据库表或页面，再等待业务逻辑补齐。

## 5. 阶段 0：建立稳定基线

### 目标

确认当前代码能构建、测试、启动，并把认证改动从“工作区状态”变成可追踪的基线。

### 工作项

1. 检查 Git 工作区，区分已有功能、认证改动和临时日志；
2. 运行后端测试：`backend\\mvnw.cmd test`；
3. 运行前端测试：`npm --prefix frontend run test -- --run`；
4. 运行前端构建：`npm --prefix frontend run build`；
5. 修复阻断构建的问题；
6. 更新 README，准确列出当前已完成和未完成模块；
7. 将认证模块按一个独立提交整理，提交信息使用中文规范。

### 验收标准

- 后端测试通过；
- 前端测试和构建通过；
- 新开发者按 README 可以启动服务；
- Git 历史中能明确找到认证模块提交。

## 6. 阶段 1：完成可演示的认证和全局 RBAC

### 目标

满足老师对身份认证、验证码、登录方式、注册、找回密码和 RBAC 基础框架的要求。

### 保留的角色

```text
ROLE_USER   普通用户
ROLE_ADMIN  系统管理员
```

### 工作项

1. 确认密码登录和至少一种验证码登录可用；
2. 确认图形验证码可展示和校验；
3. 确认注册、忘记密码和提示信息可用；
4. 确认 JWT、刷新令牌和登出黑名单可用；
5. 初始化普通用户和管理员角色；
6. 保证普通注册用户默认只有 `ROLE_USER`；
7. 为管理员接口增加 `@RequireRole("ROLE_ADMIN")`；
8. 增加管理员查看用户列表接口；
9. 增加普通用户访问管理员接口返回 `403` 的测试；
10. 增加管理员访问成功的测试。

### 验收场景

```text
注册普通用户 → 登录 → 访问自己的笔记成功
普通用户 → 访问 /api/admin/users → 403
管理员登录 → 访问 /api/admin/users → 200
```

这一阶段完成后，已经可以向老师展示一条完整的鉴权和授权闭环。

## 7. 阶段 2：把笔记和文件统一成可管理资料

### 目标

让现有笔记和 Markdown 文件真正成为知识库的输入资料。

### 建议新增模型

```text
knowledge_base
  id, owner_id, name, description, created_at, updated_at

knowledge_base_member
  knowledge_base_id, user_id, member_role, created_at

knowledge_base_resource
  knowledge_base_id, resource_type, resource_id
```

其中 `member_role` 第一版只取：

```text
OWNER   知识库拥有者
EDITOR  可以上传、编辑和删除资料
VIEWER  只能查看和提问
```

### 工作项

1. 创建知识库表和成员表；
2. 每个新用户自动创建一个默认知识库，或提供创建页面；
3. 让笔记和 Markdown 文件可以加入知识库；
4. 列表查询必须按知识库成员关系过滤；
5. 知识库拥有者可以添加和移除成员；
6. `EDITOR` 可以维护资料；
7. `VIEWER` 不能修改或删除资料；
8. 所有相关 Service 查询都检查知识库权限；
9. 增加越权测试。

### 验收场景

```text
用户 A 创建知识库
用户 A 添加用户 B 为 VIEWER
用户 B 可以查看资料和提问
用户 B 不能上传、修改或删除资料
用户 A 可以管理成员和资料
用户 C 不属于知识库，访问返回 403
```

这一步是“仿禅道 RBAC”真正有意义的地方：同一个用户在不同知识库中可以拥有不同权限。

## 8. 阶段 3：稳定索引流水线

### 目标

保证资料上传后，用户能看到明确的索引状态，并且失败可以重试。

### 工作项

1. 上传资料后状态为 `PENDING`；
2. 异步完成切片、Embedding 和 Milvus 写入；
3. 成功改为 `INDEXED`；
4. 失败改为 `FAILED` 并保存错误原因；
5. 前端展示索引状态；
6. 提供重新索引按钮；
7. 资料删除时清理数据库切片和 Milvus 向量；
8. Embedding 未配置时给出明确的开发环境提示；
9. 用假的 Embedding 客户端完成测试，不依赖真实外部服务。

### 验收标准

- 上传一个 Markdown 文件后能看到状态变化；
- 索引失败不会阻塞文件列表；
- 点击重试可以重新提交任务；
- 删除资料后不能在向量库中继续检索到该资料。

## 9. 阶段 4：先做最小问答闭环

### 目标

让现有索引真正服务于一个用户可见的功能：在知识库中提问并返回引用。

### 第一版不追求复杂模型能力

先实现固定、清晰的 RAG 流程：

```text
问题
  ↓
生成问题向量
  ↓
按知识库和用户权限过滤 Milvus
  ↓
取 Top-K 切片
  ↓
调用一个模型生成回答
  ↓
返回回答和引用切片
```

### 建议接口

```text
POST /api/knowledge-bases/{id}/query
GET  /api/knowledge-bases/{id}/queries
```

### 返回结构至少包含

```json
{
  "answer": "回答内容",
  "citations": [
    {
      "resourceId": 1,
      "resourceType": "DOCUMENT",
      "content": "引用的资料片段",
      "score": 0.91
    }
  ]
}
```

### RBAC 要求

- `OWNER`、`EDITOR`、`VIEWER` 可以提问；
- 不属于知识库的用户不能提问；
- 检索条件必须包含 `knowledge_base_id` 或等价的数据范围条件；
- 不能因为知道资源 ID 就检索到其他知识库的内容。

## 10. 阶段 5：补充产品功能

只有 MVP 主链路稳定后，再按下面顺序扩展：

1. 标签和搜索；
2. 知识库成员邀请；
3. 分享链接；
4. 登录审计和权限变更审计页面；
5. 主题定制；
6. 更细的角色和动态权限管理。

## 11. 推荐的页面顺序

前端不要同时开发所有页面，按用户主流程实现：

1. 登录/注册/找回密码；
2. 知识库列表和创建；
3. 知识库详情；
4. 资料列表和上传；
5. 资料预览和索引状态；
6. 成员管理；
7. 问答页面和引用展示；
8. 管理员用户列表。

## 12. 每个阶段的提交和验收方式

每一阶段使用独立分支或独立提交，建议格式：

```text
docs: 明确 MVP 执行边界
feat: 完成认证与全局 RBAC
feat: 增加知识库和成员权限
feat: 稳定资料索引状态流转
feat: 增加知识库问答闭环
```

每次提交前至少执行：

```powershell
backend\\mvnw.cmd test
npm --prefix frontend run test -- --run
npm --prefix frontend run build
```

如果改了 Docker 或环境变量，再执行：

```powershell
docker compose -f deploy/docker-compose.yml --env-file deploy/.env.example config
```

## 13. 最终可演示脚本

完成阶段 0 到阶段 4 后，可以按下面步骤演示：

1. 注册用户 A 和用户 B；
2. 用户 A 登录并创建知识库；
3. 用户 A 将用户 B 加入为 `VIEWER`；
4. 用户 A 上传 Markdown 资料；
5. 等待资料状态变为 `INDEXED`；
6. 用户 B 登录并查看资料；
7. 用户 B 对知识库提问并看到引用；
8. 用户 B 尝试删除资料，得到 `403`；
9. 管理员登录并查看用户列表；
10. 普通用户访问管理员接口，得到 `403`。

这个演示同时覆盖了：身份认证、验证码、JWT、RBAC、数据范围、资料管理、索引和知识库问答。

## 14. 当前最应该做的三件事

不要马上添加新角色或新页面，先按这个顺序执行：

1. **稳定阶段 0**：跑通测试，整理当前认证工作区，修正文档与代码不一致；
2. **完成阶段 1**：把 `ROLE_USER` / `ROLE_ADMIN` 和管理员接口做成可测试的闭环；
3. **开始阶段 2**：增加知识库和成员关系，让 RBAC 进入真实业务。
