# 数据持久化模块 — 完成方案

> 分支：`feat/data-persistence`
> 范围：管理后台「数据持久化」整条链路（前端页面 → 接口 → 服务 → 落盘产物 + 定时调度）
> 技术约束：数据访问统一走 MyBatis / MyBatis-Plus（项目既有 `mapper-locations: classpath*:/mapper/**/*.xml`），不引入 JPA、不直写 JdbcTemplate。

---

## 1. 结论先行

现在这个模块**只完成了「配置项的录入与回显」**，配置本身是死数据：

- 前端把 4 个字段拼成 JSON 写进 `instance_setting.PERSISTENCE`；
- 后端全仓库**没有任何一处读取 `PERSISTENCE`**（`grep -rn "PERSISTENCE" backend/src/main` 无结果）；
- 页面承诺的「关闭后仅在当前会话内保留数据」「按周期生成数据快照」「备份保留天数」三项**全部没有实现载体**：没有备份任务、没有调度器、没有备份文件、没有历史记录、没有恢复入口。

因此本方案的核心不是「把表单做得更好看」，而是给这个配置**接上它本该驱动的四个真实能力**：配置生效（类型化读写 + 校验）、状态可见（真实存储用量）、手动/自动备份（产出可校验的归档文件）、按保留期清理与恢复。

完成后该页面的一句话定位应改为：**「实例业务数据的快照备份与恢复策略」**——业务数据本来就在数据库里持久化，这个模块负责的是**快照与灾难恢复**，而不是「决定数据存不存」。

## 3. 目标与非目标

### 3.1 目标

1. **配置有唯一事实来源**：`PersistenceSetting` 在后端定义、后端校验、后端补默认值；前端只做展示与提交。
2. **状态可见**：页面能显示数据库实际大小、各表行数、向量库条数、备份目录是否可写、上次备份时间与结果。
3. **手动备份可用**：点一下就能生成一个带清单与校验和的归档，可下载、可删除、可校验完整性。
4. **自动备份与保留期生效**：按配置周期跑，超出保留天数的归档自动清理，且清理只碰本应用生成的文件。
5. **恢复可用且安全**：恢复前强制生成「恢复前快照」，两步确认，失败可回退；恢复后引导重建向量索引。
6. **全过程仅管理员可用**，并且路径、文件名、删除范围都有白名单约束。

### 3.2 非目标（明确不做，避免范围失控）

- **不接管 MySQL 数据目录**：运行中的数据库不可能通过 Web 改 `datadir`，`storagePath` 只表示**备份归档的落盘根目录**。
- **不备份 Milvus 向量**：向量可由 `note` / `document` 正文重建，归档中只记「需要重建索引」的标记；恢复后走既有 `IndexingService.schedule` 重建。
- **不做跨实例迁移/多租户导出**：本期是整实例快照，不做单用户导出。
- **不做「关闭持久化后数据只在会话内」**：这个能力在当前架构下不成立（DB 就是持久层），必须改文案而不是造一个假开关。
- **不引入 mysqldump 等外部二进制**：容器镜像里未必有，且版本/参数差异大；用 MyBatis 做**逻辑导出**，可测、可控、可跨版本。

## 4. 语义定义（先对齐，再写码）

| 概念 | 定义 | 说明 |
| --- | --- | --- |
| 持久化 | 业务数据落在 MySQL（`memo` 库），由数据库自身保证 | 现状已成立，本模块不改这一点 |
| 快照 / 备份 | 某个时刻全库逻辑导出形成的单个归档文件（`.zip`） | 本模块的产物 |
| `storagePath` | **备份归档根目录**（绝对路径；相对路径按进程工作目录解析） | 默认 `${AIREVIEW_BACKUP_DIR:./data/backups}` |
| `autoBackup` | 是否按 `backupCron` 周期自动生成快照 | 关闭仅停止自动快照，不影响业务数据 |
| `retentionDays` | 自动清理时保留的最近天数（手动标记 `KEEP` 的归档不受影响） | 1–3650 |
| 恢复 | 用归档覆盖当前库中的 18 张业务表 | 破坏性操作，需 `confirm=RESTORE` |

## 5. 总体架构

```
AdminView（数据持久化面板）
   │  GET/PUT  /api/admin/persistence/setting
   │  GET      /api/admin/persistence/status
   │  POST     /api/admin/persistence/backups            → 返回 taskId
   │  GET      /api/admin/persistence/backups?page       → 历史（backup_record 表）
   │  GET      .../backups/{id}/download | POST .../verify | POST .../restore
   ▼
PersistenceController  (@RequireRole("ROLE_ADMIN"))
   ▼
PersistenceService / BackupService / RestoreService
   ├── PersistenceSettingCodec  → instance_setting.PERSISTENCE（类型化 JSON）
   ├── BackupExecutor（单飞锁 + 异步线程池）→ 生成 zip 到 storagePath
   ├── RetentionCleaner          → 按 retentionDays 删除过期归档
   ├── BackupScheduler           → @Scheduled 每分钟检查 cron，命中即触发
   └── MyBatis
        ├── BackupRecordMapper   extends BaseMapper<BackupRecord>
        ├── PersistenceStatMapper（information_schema 统计，XML）
        └── BackupDumpMapper     （18 张表的显式列 select / batch insert，XML）
```

关键取舍：**归档由应用自己写，不依赖数据库外部工具**；**所有表名与列名写死在 XML 里，杜绝 `${}` 拼接**；**任务异步执行、状态落库**，页面刷新不丢进度。

## 6. 后端设计

### 6.1 数据模型：`backup_record`

新增一张表记录每次备份/恢复尝试（含失败），让历史与审计不依赖「扫目录」。

```sql
-- 追加到 docs/sql/schema.sql，并同步 docs/sql/migrations/002_add_backup_record.sql
CREATE TABLE IF NOT EXISTS `backup_record` (
  `id`            BIGINT       NOT NULL AUTO_INCREMENT,
  `file_name`     VARCHAR(191) NOT NULL COMMENT '归档文件名，不含目录',
  `trigger_type`  VARCHAR(16)  NOT NULL COMMENT 'MANUAL / AUTO / PRE_RESTORE',
  `status`        VARCHAR(16)  NOT NULL COMMENT 'RUNNING / SUCCESS / FAILED',
  `size_bytes`    BIGINT       NOT NULL DEFAULT 0,
  `checksum`      CHAR(64)     NOT NULL DEFAULT '' COMMENT '归档 SHA-256',
  `table_count`   INT          NOT NULL DEFAULT 0,
  `row_count`     BIGINT       NOT NULL DEFAULT 0,
  `keep_forever`  TINYINT(1)   NOT NULL DEFAULT 0 COMMENT '1=不参与保留期清理',
  `error_message` VARCHAR(512) NULL,
  `started_at`    DATETIME     NOT NULL,
  `finished_at`   DATETIME     NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_backup_file` (`file_name`),
  KEY `idx_backup_status_started` (`status`, `started_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='数据快照记录';
```

设计要点：

- `uk_backup_file` 保证同一文件不会被记两次，也防止并发产生同名覆盖；
- `keep_forever` 支持「这条别删」，避免手滑把唯一一份可用归档清掉；
- 只存元数据，字节在文件系统；`checksum` 是完整性的唯一凭据；
- 失败也要落一行（`status=FAILED` + `error_message`），否则「昨天为什么没备份」无从查起。

### 6.2 MyBatis 落点（本方案的硬约束）

全部数据访问用 MyBatis，按职责拆三个 mapper：

**a) `BackupRecordMapper extends BaseMapper<BackupRecord>`**
CRUD 与分页直接吃 MyBatis-Plus（与 `NoteMapper`、`DocumentMapper` 一致），只补两个 XML 语句：

```xml
<!-- src/main/resources/mapper/BackupRecordMapper.xml -->
<select id="selectRunning" resultMap="BaseResultMap">
  SELECT * FROM backup_record WHERE status = 'RUNNING' ORDER BY started_at LIMIT 1
</select>

<select id="selectExpired" resultMap="BaseResultMap">
  SELECT * FROM backup_record
  WHERE status = 'SUCCESS' AND keep_forever = 0 AND started_at &lt; #{before}
  ORDER BY started_at
</select>
```

**b) `PersistenceStatMapper`**（只读统计，`information_schema` + 固定表名白名单）

```xml
<select id="selectTableStats" resultType="com.aireview.dto.persistence.TableStatVO">
  SELECT table_name AS tableName,
         table_rows AS rowEstimate,
         ROUND((data_length + index_length) / 1024 / 1024, 2) AS sizeMb
  FROM information_schema.tables
  WHERE table_schema = DATABASE()
    AND table_name IN
    <foreach collection="tables" item="t" open="(" separator="," close=")">#{t}</foreach>
  ORDER BY (data_length + index_length) DESC
</select>
```

**c) `BackupDumpMapper`**（导出/导入，18 张表各一对语句，列名显式列出）

```xml
<select id="selectNotes" resultType="com.aireview.entity.Note" fetchSize="500">
  SELECT id, user_id, title, content, is_pinned, is_archived, created_at, updated_at FROM note ORDER BY id
</select>

<insert id="insertNotes">
  INSERT INTO note (id, user_id, title, content, is_pinned, is_archived, created_at, updated_at) VALUES
  <foreach collection="rows" item="r" separator=",">
    (#{r.id}, #{r.userId}, #{r.title}, #{r.content}, #{r.isPinned}, #{r.isArchived}, #{r.createdAt}, #{r.updatedAt})
  </foreach>
</insert>
```

为什么不用 `SELECT * FROM ${table}` 这种「通用 dump」：表名来自请求/配置时会变成注入面；而且恢复时 OncePerRequest 的列顺序依赖 `information_schema`，跨版本容易错位。**表名、列名全部写在 XML 里**，新增表时改 XML + 改表清单常量，改一次、审一次。

### 6.3 配置对象 `PersistenceSetting`

照 `GeneralSetting` 的既有套路（record + `defaults()` / `fromJson()` / `toJson()`），但因为有字符串与数字，用 Jackson 而不是手写 `indexOf` 解析。

```java
package com.aireview.dto;

public record PersistenceSetting(
    boolean enabled,
    String storagePath,
    boolean autoBackup,
    String backupCron,
    int retentionDays) {

    public static PersistenceSetting defaults() {
        return new PersistenceSetting(true, "./data/backups", false, "0 0 3 * * *", 30);
    }
    // fromJson / toJson 走 ObjectMapper，解析失败 → defaults()
    // normalize(): storagePath 去空白并转绝对路径；retentionDays 夹到 [1,3650]；backupCron 非法 → 默认
}
```

配套 `PersistenceSettingService`（或直接扩 `InstanceSettingService`，与 `getGeneral/upsertGeneral` 对称）：

- `getPersistence()`：无记录 → `defaults()`；JSON 损坏 → `defaults()` 并记 WARN（不再静默）；
- `upsertPersistence(setting)`：`@RequireRole("ROLE_ADMIN")`，先 `normalize` 再校验：
  - `enabled=true` 时路径不能为空，且**必须可创建、可写**（`Files.createDirectories` + 写探针文件后删除），失败抛 `BusinessException(BAD_REQUEST, "备份目录不可写：…")`；
  - `backupCron` 用 `CronExpression.isValidExpression` 校验；
  - 校验通过后再落库，**并在返回体里带回规范化后的值**，前端以返回值覆盖表单（用户能看到路径被解析成了什么）。

### 6.4 归档格式

单个 zip，文件名 `aireview-YYYYMMDD-HHmmss-<trigger>.zip`，内部结构：

```
manifest.json          # 清单与校验
data/user.jsonl        # 每张表一个 JSONL，一行一条记录
data/note.jsonl
...                    # 共 18 个
index-hint.json        # 需重建索引的资源：{"notes":[ids...],"documents":[ids...]}
```

`manifest.json`：

```json
{
  "formatVersion": 1,
  "appVersion": "0.0.1",
  "createdAt": "2026-11-19T16:30:00+08:00",
  "database": "memo",
  "tables": [
    { "name": "note", "rows": 128, "sha256": "…" },
    { "name": "document", "rows": 7, "sha256": "…" }
  ],
  "totalRows": 1350,
  "archiveSha256": "…"
}
```

写入用流式：`ZipOutputStream` → `JsonGenerator` 逐行写，`fetchSize=500` 的游标读，**不在内存里攒全量**（`document.content` 可能有 2MB/篇）。`archiveSha256` 在关闭 zip 后回读文件计算，写回 zip 需要二次写入 → 改为：`checksum` 只算「所有 `data/*.jsonl` 内容 + manifest 摘要」写入 `backup_record.checksum`，`manifest.json` 里存各表 sha256，校验时逐表比对。这样归档一次成型，不需要重写 zip。

### 6.5 备份执行流程

状态机：`RUNNING → SUCCESS | FAILED`，全程写 `backup_record`。

1. **单飞锁**：`ReentrantLock.tryLock()` + 查 `selectRunning()`；已有 `RUNNING` 记录直接拒绝（`409 已有备份任务在执行`）。多实例部署时叠加 Redis `SETNX aireview:backup:lock`（项目已有 Redis），失败即拒绝。
2. 读配置：`enabled=false` 且 `trigger=MANUAL` 允许（人工兜底），`enabled=false` 且 `AUTO` 直接跳过并记 debug。
3. 建 `backup_record`（`RUNNING`）。
4. 逐表 dump 到 `<storagePath>/tmp/<uuid>/`，再整体 `Files.move` 成最终 zip（原子改名，避免半成品被当成可用归档）。
5. 计算 checksum、行数，更新记录为 `SUCCESS`；异常则 `FAILED` + `error_message`，并清理 tmp。
6. 触发 `RetentionCleaner`。

线程模型：`POST /backups` 立刻返回 `202 + taskId(=recordId)`，执行交给 Spring 的**有界线程池**（`ThreadPoolTaskExecutor`，core 1 / max 2 / queue 4，队列满返回 429），不占用 Web 线程；进度由前端轮询 `GET /backups/{id}`。

### 6.6 恢复流程

破坏性操作，四道闸：

1. **前置校验**：归档存在、`checksum` 与库中记录一致、`manifest.formatVersion` 受支持（当前 1）。
2. **自动安全快照**：先以 `trigger=PRE_RESTORE`、`keep_forever=1` 生成一份当前库快照；这份失败则**直接中止恢复**。
3. **事务内覆盖**：`@Transactional` 单事务内按依赖顺序 `DELETE`（反向）+ `batch insert`，每 500 行一条语句；任一步抛错整体回滚（表无外键约束，回滚靠事务本身）。
4. **恢复后处理**：清空 `document_chunk` 之外不做任何向量操作；读取 `index-hint.json`，把所有笔记/文档重新 `IndexingService.schedule`；返回 `{ restoredRows, reindexScheduled }` 供前端提示「向量正在重建」。

会话/令牌影响：`user` 表被覆盖后，当前管理员令牌仍有效（JWT 无状态 + `token_version` 来自库中该用户行），因此恢复前提示「若归档来自旧时间点，其他用户可能需要重新登录」。

### 6.7 调度与保留清理

- `PersistenceScheduleConfig` 上加 `@EnableScheduling`（目前项目**没有任何调度器**，这是首次引入，需在 PR 说明里点明）。
- `BackupScheduler` 每 60 秒触发一次，读 `PersistenceSetting`：
  - `autoBackup=false` → 直接返回；
  - 用 `CronExpression.next(lastCheckTime)` 判断「上一分钟内是否应当触发」，命中则 `backupService.start(AUTO)`；这样避免了「改 cron 要重启进程」。
  - 同时给出 `nextRunAt`（供 `status` 接口展示）。
- `RetentionCleaner`：`selectExpired(now - retentionDays)` → 删文件（仅当文件名匹配 `^aireview-\d{8}-\d{6}-(manual|auto|pre-restore)\.zip$` 且父目录 == `storagePath`）→ 删记录；文件已不存在也删记录并 WARN。

### 6.10 安全边界

- 路径：只接受「配置的根目录」下的写入；下载/删除/恢复都先 `Path.normalize()` 后断言 `startsWith(root)`，防 `../` 穿越。
- 文件名：只认 `backup_record` 里登记的 `file_name`，不接受请求传文件名。
- 大小：单归档超过 `max-archive-mb` 中止并 FAILED，避免磁盘打满。
- 恢复：`confirm` 字面量校验 + 前置安全快照 + 单事务，缺一不可。
- 审计：`backup_record.trigger_type` + `sys_login_log` 已有的管理员审计口径一致；恢复操作额外写 INFO 日志（谁、哪个归档、影响行数）。
- 明文风险：归档含 `user.password` 哈希与 `personal_access_token`。**归档目录权限应为 700**，下载接口只对 ADMIN 开放，页面明确提示「归档内含凭据哈希，请勿外传」。

### 7.3 交互细节

- **保存**：前端只做轻校验（天数范围、路径非空当 `enabled`）；以 `PUT` 返回值回填表单（展示后端规范化后的绝对路径），成功 toast「配置已保存」。
- **立即备份**：点击后按钮进入 `备份中…` 并禁用所有写操作 → 每 2 秒 `GET /backups/{id}` 轮询，`SUCCESS/FAILED` 停止；成功后刷新历史与概览，失败展示后端 `error_message`。轮询要有上限（60 次）与页面卸载清理。
- **恢复**：模态框展示归档时间/行数/大小 → 输入 `RESTORE` 才可点确认 → 提示「将先生成恢复前快照，随后覆盖 18 张业务表」→ 完成后提示「向量索引正在后台重建」。
- **状态可视化**：`RUNNING` 行用进度条（按已完成表数 / 18 估算），不做假精度。
- **空/错/加载**：历史为空时给「还没有备份，点右上角立即备份」引导；`status.directoryWritable=false` 时顶部红条提示并禁用「立即备份」。
- **响应式**：历史表在 <900px 折成卡片列表（沿用现有 `.table` → `.list` 断点写法）。

### 7.4 文案修正（必须改，属于事实性纠错）

| 现在 | 改为 |

## 11. 风险与取舍

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 全量逻辑导出对大数据量慢、占 CPU/IO | 备份期间接口变慢 | 流式逐表导出 + 有界线程池（1–2 线程）+ 默认凌晨 cron；后续可按表分批/增量 |
| 归档含密码哈希与 PAT | 泄露即凭据风险 | 目录 700、仅 ADMIN 可下载、页面显式警示、不落公网存储 |
| 恢复覆盖 `user` 表 | 其他用户会话/权限错乱 | 恢复前提示 + `PRE_RESTORE` 快照可回退；JWT `token_version` 机制已在，必要时提示重新登录 |
| 新增 `@EnableScheduling` 与线程池 | 引入后台线程，测试环境可能干扰用例 | 配置类用 `@Profile("!test")` 或属性开关关闭；测试里直接调用 service 方法验证逻辑，不依赖真实调度 |
| MyBatis 逐表写 XML 冗长 | 18 张表 36 条语句，新增表易漏 | 表清单集中在一处常量 + 单测断言「XML 覆盖的表 == 常量表」，漏写直接测试失败 |
| `storagePath` 与容器卷的关系 | 路径在容器内，宿主机看不到 | 部署文档注明「必须挂载持久卷到该目录」，`deploy/docker-compose.yml` 增加对应 volume |
